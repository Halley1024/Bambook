考察是否理解机制，而不只会用语法
01请解释所有权、借用和生命周期。它们分别解决什么问题？给一个你在项目中遇到的具体例子。重点

答题检查点

  • 所有权决定值的唯一管理者与析构时机；借用允许临时访问，引用受作用域约束。
  • 不可变借用可并存，可变借用在同一时刻独占，编译期阻止悬垂引用与数据竞争。
  • 结合项目讲清楚为什么跨线程请求要把路径、查询参数转成拥有所有权的 String，而不能把调用方借用的 &str 带进 worker。
  • 区分生命周期标注与延长生命周期：标注描述关系，不会让数据活得更久。
追问：什么时候用 &str，什么时候用 String？clone 是否一定昂贵？
02Rust 的 Send 和 Sync 是什么？为什么 MuPDF 文档句柄不能跨线程共享时，worker + channel 是合适的边界？重点
  • Send 表示值可安全转移到另一线程；Sync 表示对类型的共享引用可安全跨线程使用。
  • 若底层句柄不是 Send/Sync，不应绕过类型约束用 unsafe 强行共享；把句柄留在创建它的 worker 线程，由消息传递访问。
  • 项目模型：每个 PDF session 一个串行 worker/channel，文档间并行、同一文档请求串行。
  • 说明这个选择换来了线程安全和顺序明确，也带来排队、关闭、阻塞等待、worker 崩溃和背压等需要处理的问题。
追问：如何让 worker panic 后调用方不永久等待？如何优雅关闭并确认线程退出？
03Mutex、RwLock、Atomic 和消息传递各适合什么场景？本项目中为什么用 Mutex<HashMap> 管 session、channel 串行化 PDF 操作？
  • Mutex 保护短临界区的共享可变状态；RwLock 适用于读多写少但有写者饥饿/升级等复杂度；Atomic 用于简单原子状态或计数；channel 传递工作与所有权。
  • session map 的锁只用于查找/插入/移除 sender，避免持锁等待 worker 回复；实际文档操作在线程内串行执行。
  • 注意锁中毒、死锁、锁粒度，以及不要持锁做阻塞 I/O 或等待 channel。
04Result、Option、? 和 thiserror 如何帮助构建清晰的错误边界？哪些错误适合向前端暴露？
  • 用 Result 表达可恢复失败，用 Option 表达值可能缺失；? 传播错误但不等于处理错误。
  • 基础设施保留底层错误上下文，映射为领域/AppError；IPC 层将其稳定序列化，避免泄露本地路径、密码或内部栈信息。
  • 区分无效密码、session 不存在、路径不可访问、MuPDF 错误、状态锁不可用，并讨论哪些可重试。
追问：如何保留 source error？什么时候定义自有错误 enum，什么时候使用 anyhow？
05trait、泛型和动态分发分别解决什么问题？项目中的 ports/adapter 为什么使用 trait？
  • trait 定义行为契约；泛型静态分发利于内联但会产生单态化；dyn trait 动态分发提供运行时替换与异构集合。
  • application port 隔离 PDF 引擎、文件存储、Markdown parser 等实现；基础设施 adapter 接入 MuPDF/文件系统。
  • 由此可以测试业务服务而不启动 GUI/真实解析器，并避免第三方类型污染 domain/API。
追问：trait object 的对象安全条件？async fn trait 的常见处理方式？
06Rust 的 async/await 如何工作？阻塞式 MuPDF 操作放进 async command 会有什么风险？
  • Future 通常惰性执行，由 executor poll；await 在未就绪时让出执行权，不会自动把同步阻塞操作变为异步。
  • 阻塞解析/磁盘 I/O 若占住 async runtime worker，可能拖慢其他请求；可用专用线程池、spawn_blocking 或现有专属 worker。
  • 讨论取消语义：丢弃 Future 不必然停止已经开始的底层任务；request id/generation 可以让过期搜索尽早停止。
07Vec、String、HashMap 的常见复杂度和内存行为是什么？在什么情况下会发生扩容或 reallocation？
  • Vec/String 连续存储，push 摊还 O(1)，扩容可能重分配并使内部指针/引用失效。
  • HashMap 平均查找 O(1)，最坏情形更差；迭代顺序不稳定，不应依赖顺序输出。
  • 需要可预测容量时 reserve；不要把裸指针或引用跨越可能导致容器变动的边界。

二、Bambook 项目深挖

建议用「问题—设计—取舍—验证—复盘」回答
08请用 2 分钟介绍 Bambook。你负责了什么？Rust 后端最有技术含量的部分是什么？重点项目
  • 讲清桌面 PDF 阅读 + Markdown 编辑定位、Tauri/React/Rust 边界，以及自己主导的后端架构。
  • 挑一个主线：MuPDF 非线程安全句柄的 worker 模型、结构化 Markdown AST/edit revision，或原子导出。
  • 给出真实规模/指标/故障案例；区分已实现、部分实现、待验收能力，避免把 README 规划项说成完成。
  • 收尾说清个人贡献与团队/开源依赖边界。
09为什么采用 domain / application / infrastructure / commands 分层？一次打开 PDF 的调用链如何流动？重点项目
  • 从 Tauri command 接收/校验 DTO，调用 application service；service 通过 port 访问 PDF engine/session repository；infrastructure 用 MuPDF 实现，返回 domain model，再映射 DTO。
  • 解释依赖方向：业务规则不依赖 Tauri/MuPDF 细节；adapter 可替换，service 可隔离测试。
  • 指出分层成本：接口与映射增多；小型纯转换逻辑不必过度抽象。
追问：如果要增加另一种 PDF 引擎，哪些模块会改变？哪些不该知道 MuPDF 类型？
10为什么每个 PDF session 使用单线程 worker？channel 请求从发起到返回经历什么？重点项目
  • 为不可跨线程访问的 MuPDF Document 建立线程封闭；请求枚举承载 authenticate/page structure/render/close，reply channel 返回 AppResult。
  • 文档间并行，同一文档操作串行，避免共享句柄竞争；session map 保存 sender。
  • 分析同步 recv 对 Tauri command 的阻塞、请求队列无界、关闭时 worker 是否及时退出、sender 断开时错误映射及线程泄漏。
  • 提出改进：有界队列/背压、超时或异步响应、JoinHandle 回收、panic 捕获/状态标记、指标和压测。
11如何证明 worker 模型没有数据竞争？如何测试 session 生命周期和请求顺序？
  • 安全 Rust 类型约束 + Document 仅在 worker 栈/线程持有 + 外部只能发命令，是设计证明的一部分。
  • 测试双 session 并发、同 session 顺序、无效 session、认证成功/失败、关闭后调用、worker 退出。
  • 对 MuPDF 用 fake port 做 application 层单元测试；少量真实 PDF 做集成/回归测试；记录耗时与内存。
  • 指出测试难点与当前确有的覆盖范围，不能虚构已跑过的压测。
12Markdown 为什么返回结构化 AST，而不是直接返回拼接好的 HTML？如何避免 XSS？重点项目
  • AST 提供可验证类型、source range、outline、编辑定位，前端可按组件渲染，避免后端返回的 HTML 与交互/样式强耦合。
  • HTML/链接仍是信任边界：解析后对 URL scheme 做白名单/清理，渲染时转义文本，原始 HTML 默认禁用或严格 sanitizer；不要把未可信字符串直接 innerHTML。
  • 说明 Markdown 允许的链接/图片协议、data/javascript URL 和外链打开策略。
追问：AST source range 是 UTF-8 byte offset 还是 UTF-16 code unit？前后端如何一致？
13编辑协议里的 UTF-16 edit range 和 revision 冲突检查解决什么问题？并发编辑如何避免覆盖新内容？
  • 浏览器编辑器索引常按 UTF-16 code unit，而 Rust String 索引是 UTF-8 byte offset；必须明确协议单位并做边界转换校验。
  • 每个 session 带 revision，edit 携带期望 revision；不匹配则拒绝/要求客户端重新取结构，避免过期 patch 静默覆盖。
  • 验证 surrogate pair、emoji、中文、多 edit 排序/重叠、越界和非法边界；描述冲突 UX 或未来 OT/CRDT 需求（若多人协作）。
14文件保存/导出为什么采用同目录临时文件 + 校验 + 原子替换？原子性边界是什么？重点项目
  • 先生成相邻临时文件，flush/sync，验证输出可重新解析，再 rename/平台原子替换，减少失败时破坏旧文件的风险。
  • 同目录通常确保同一卷；原子替换保证目录项切换原子性，不等于所有硬件/文件系统上断电绝对持久，也不自动解决并发写覆盖。
  • 说明临时文件 guard 清理、目标文件已存在、Windows 替换 API、权限/磁盘满、崩溃残留与恢复策略。
15路径来自前端或文件名时，如何防止路径穿越、错误覆盖和符号链接问题？
  • 前端传入不等于可信：后端规范化/校验允许根目录、文件类型、扩展名、目标冲突和权限。
  • 拒绝 .. 绕出根目录；考虑 canonicalize 与 TOCTOU、符号链接、大小写/Unicode 路径等平台差异。
  • 文件对话框返回路径仍要在后端校验；避免把任意路径拼接到 storage root 后直接写。
16搜索如何把 Unicode 规范化后的命中映射回 PDF 原始字符和 MuPDF 坐标？有什么边界情况？
  • NFKC、大小写折叠、空白折叠会改变字符数量；保存每个 normalized unit 对应的 source byte range、行号与 rect，命中区间才能映射回原文几何范围。
  • 处理组合字符、全角、连字展开、换行断词连字符、跨 span/行命中、重叠命中、Unicode byte boundary。
  • 不同字符共享矩形、跨行命中如何返回多个 rect；坐标空间必须与渲染/批注统一，缩放只在显示层转换。
17搜索取消与过期结果丢弃如何工作？generation/requestId 是否能真正中断正在运行的解析？
  • requestId 标识查询；新请求更新 generation，worker 在页/批次边界检查当前 generation，取消时 compare_exchange 避免误取消新请求。
  • 过期 response 即使算完也应由调用端丢弃；取消粒度取决于检查点，不能中断不支持取消的单次底层调用。
  • 说明缓存索引何时清空（如密码认证后）、内存上限和大型 PDF 页面扫描的响应性。
18Tauri IPC 的安全边界在哪里？如何避免把文件系统权限交给任意前端代码？
  • command 是能力边界：最小化暴露命令、参数校验、权限/窗口隔离、限制可访问路径；Rust 后端负责可信文件访问。
  • 前端 repository 封装 IPC，组件不直调任意命令；DTO 限定数据量与字段。
  • 关注外部链接、导入内容、插件/脚本、日志脱敏和 release 构建配置。
19如果保存请求连续到达，怎样处理脏状态、重复保存与 close race？
  • 明确 session 状态机：Open/Dirty/Saving/Closing/Closed；用 revision/version 判断保存完成后是否仍然干净。
  • 同一文档写入串行化或 compare-and-swap；关闭前等待/取消保存并尊重失败；保存成功后再释放资源。
  • 前端 close coordinator 的两阶段事务先收集 Save/Discard/Cancel 决策，再执行破坏性关闭，避免用户取消时内容已丢失。
