0这份文档怎么用

它和 面试复习-Bambook架构追问.html 是配套的，不是替代。

那份文档是「问什么、答什么」的清单——用来临场检索。这一份是「为什么会这样」的原理讲解——用来真的把机制搞懂。区别在于：清单背下来能在面试里过关，原理搞懂了才能在追问三层之后还站得住。

所以这份文档的每一节都按同一个结构写：

  1. 一句话结论（先建立正确直觉）

  4. 代码依据（真实文件与行号，可以当场打开核对）
  5. 如果换个做法会怎样（反例——这是面试拉开差距的地方）
  6. 面试口播稿（一段可以直接说出口的话）
一句方法论的提醒

这个项目里，README 是设计意图（写"打算怎么做"），代码是现状（写"实际怎么做"）。两者不一致时永远以代码为准。这份文档里的每一条结论都标了文件路径——如果你在面试前一晚只剩两小时，只读每一节的「一句话结论」和「反例」，性价比最高。

1全局地图：先看清依赖箭头往哪指

所有后续专题都建立在这张图上。

结论：这个项目的分层不是「按文件夹分门别类」，而是用依赖方向约束变化范围。application 层不认识 infrastructure 层——这才是分层的实质，其余都是形式。

1.1 四层结构与依赖方向

为什么叫「依赖倒置」，倒置在哪

朴素写法里，业务代码会直接 use mupdf::Document——于是业务逻辑依赖于具体库，库一换，业务代码全改。这里的做法是：在 application 层先定义 trait（PdfEngine），然后让 infrastructure 反过来去实现它。trait 属于内层，实现属于外层，依赖箭头因此指回内层。这就是"倒置"。

它的直接收益可以精确指出来：application/services/pdf_document_service.rs 里写的是 engine: Arc<dyn PdfEngine>，全程没有出现过 mupdf 这四个字母。所以换渲染引擎、加一个 Mock 引擎做测试，改动都被挡在 infrastructure 内部。

反例：如果不分层会怎样

最典型的后果不是"代码难看"，是测试必须启动真实 DLL 和真实文件系统。现在的 mupdf_engine.rs 能写出 opens_extracts_and_renders_a_pdf_in_its_session_worker 这种测试，是因为 engine 本身被隔离在一个文件里；如果 MuPDF 调用散落在 20 个文件里，任何一个单元测试都会变成集成测试。

1.2 一次翻页到底走了哪些环节

把这条链路记住，后面所有专题都是它的局部放大。

这里藏着一个容易被忽略的小设计

第 ③ 步的缓存键是 sessionId:pageIndex:量化scale，scale 会先做 Math.round(scale * 1000) / 1000。因为浮点数来自连续缩放操作，同一个视觉尺寸可能算出 1.5000000000000002 和 1.4999999999999998——不量化的话，缓存命中率会低到几乎失效，每次滚动都在重新渲染。

2MuPDF 与 FFI 边界：整个项目最硬的技术点

如果你在面试里只能深入讲一个话题，讲这个。

结论：MuPDF 用 setjmp/longjmp 做错误处理，而 longjmp 一旦跨过 Rust 栈帧就是未定义行为；同时 fz_context 存在线程本地存储里，所以一个文档只能在创建它的那个线程上使用。这两条约束共同解释了项目里"每会话一个专属线程"这个看起来很奇怪的设计。

2.1 问题从哪来：MuPDF 的错误处理不是 return code

绝大多数 C 库用返回值报错（返回 NULL 或负数，再给你一个 errno）。MuPDF 不是。它用的是 C 标准里的 setjmp/longjmp——本质上是一次非局部的跳转：在某个位置埋一个"锚点"，出错时直接从深层函数跳回那个锚点，中间所有函数的调用栈被直接丢弃。

fz_try(ctx)          // 展开后 = if (setjmp(ctx->error.jmp_buf) == 0) {
{
    page = fz_load_page(ctx, doc, 0);   // 深层某个函数里 throw 了
}
fz_catch(ctx)
{
    // 通过 longjmp 直接跳到这里，fz_load_page 内部所有栈帧被丢弃
}

这个机制在纯 C 里是自洽的：C 没有析构函数，栈帧被丢弃也没有副作用。但它会穿过 Rust——而 Rust 的栈帧里可能有 Vec、String、MutexGuard、Drop 实现。跳过去就等于把这些析构全部跳过。

2.2 代码依据：错误是怎么被"接住并翻译"的

先在 C 侧定义一个宏，把"跳转 + 保存错误"打包成普通函数的样子（native/mupdf-sys/wrapper/internal.h）：

#define TRY_CATCH(ty, init, call)          \
do {                                       \
    ty result = init;                      \
    fz_try(ctx)                            \
    {                                      \
        result = call;                     \
    }                                      \
    fz_catch(ctx)                          \
    {                                      \
        mupdf_save_error(ctx, errptr);     \
    }                                      \
    return result;                         \
} while (0)

错误内容从 MuPDF 的上下文里取出，堆分配后交给调用方（wrapper/error.c）：

void mupdf_save_error(fz_context *ctx, mupdf_error_t **errptr) {
    int type = fz_caught(ctx);                  // 错误码
    const char *message = fz_caught_message(ctx); // 错误文本
    mupdf_error_t *err = malloc(sizeof(mupdf_error_t));
    err->type = type;
    err->message = strdup(message);
    *errptr = err;
}

Rust 侧执行"翻译"，把 out-param 转成 idiomatic 的 Result（native/mupdf-rs/src/error.rs）：

macro_rules! ffi_try {
    ($func:ident($($arg:expr),+)) => ({
        let mut err = ptr::null_mut();
        let res = $func($($arg),+, (&mut err) as *mut *mut mupdf_error_t);
        // 错误指针非空 → 转成 Err，并负责释放这次 malloc
        NonNull::new(err).map_or(Ok(res), |err| Err(ffi_error(err)))
    });
}
注意 ffi_error 里那一步 mupdf_drop_error

C 侧 malloc 出来的错误结构是跨语言传递的堆内存，必须由 Rust 侧显式释放——这就是为什么 ffi_error 在读走 code 和 message 之后立刻调用 mupdf_drop_error(ptr)。这类"谁分配谁释放"的约定，是 FFI 代码里最容易出错、也最值得在面试里主动提一句的细节。

2.3 第二条约束：为什么必须有"每会话一个专属线程"

这是整个后端最反直觉的设计，但它的理由非常具体。

看 native/mupdf-rs/src/context.rs：

thread_local! {
    static LOCAL_CONTEXT: RefCell<RawContext> =
        const { RefCell::new(RawContext(ptr::null_mut())) };
}

impl Context {
    pub fn get() -> Self {
        LOCAL_CONTEXT.with(|ctx| {
            // 本线程还没有 context → 从 BASE_CONTEXT 克隆一个，存进本线程的 TLS
            // 已经有了 → 直接复用
        })
    }
}

fz_context 是线程本地的。而 Document 只是一个裸指针 *mut fz_document，它是在某个线程的 context 上分配出来的。MuPDF 内部会把持有该文档的 错误锚点（jmp_buf）、锁状态、内存 store、字体缓存全都挂在这个 context 上。

2.4 这个设计的连带收益

  • 天然串行化。同一个 PDF 的渲染和取文字不会并发，不需要额外的锁。
  • 关闭是确定的。Request::Close 投进 channel 后 worker 的 while let 循环 break，线程退出，Document 的 Drop 在正确的线程上执行，fz 资源正常释放。
  • 崩溃被隔离在一处。如果某个畸形 PDF 触发了 MuPDF 内部问题，影响范围被限制在这一个线程，而不是整个进程的任意线程。
反例：如果不这么做

最"自然"的写法是引擎里放一个 Mutex<Document>，谁要渲染谁去加锁。这在功能上也能跑——因为锁保证了同一时刻只有一个线程在访问。但它错在：mutex 保证的是"互斥"，不是"同一个线程"。线程 A 创建文档、线程 B 加锁使用，B 用的是 B 的 fz_context。这属于"能跑但不符合库的契约"，会在某个版本升级或某个特殊 PDF 上暴露出来。面试时把这一点讲清楚，能显示你不是照着代码抄，而是理解了约束。

「MuPDF 的异常为什么不能穿过 Rust？」

"MuPDF 用 setjmp/longjmp 报错，本质是非局部跳转。如果让 longjmp 从 C 帧跳回时越过 Rust 栈帧，那些帧里的 Drop 就全被跳过了——句柄泄漏、MutexGuard 死锁，而且是标准意义上的 UB。项目的做法是在 C wrapper 里用 TRY_CATCH 宏把 fz_try/fz_catch 闭合在同一个 C 函数帧内，错误通过 mupdf_error_t ** out-param 写出去，C 函数正常 return，Rust 侧再把非空错误指针翻译成 Result。这样跳转从未跨出 C 的边界。"

「那为什么每个 session 要单独一个线程？」

"因为 fz_context 在 mupdf-rs 里存在线程本地存储。文档是在某个线程的 context 上创建的，它的错误锚点、锁和内存 store 都挂在这个 context 上。如果换个线程去用它，MuPDF 拿到的是那个线程的 context，状态对不上。Mutex 只能保证互斥，保证不了'同一个线程'，所以我用 mpsc 把请求序列化到创建文档的那一个线程上执行。副作用是同一文档的操作天然串行，连锁都省了。"

3渲染链路与缓存：两个 LRU 为什么不一样

这一节是整份清单里最能体现「你想过边界条件」的地方。

结论：structureCache 只限条数（24），renderedPageCache 同时限条数（10）和字节数（64MB）。因为文字结构的体积是稳定的，而页面位图的体积随缩放剧烈变化——只按条数淘汰，会在高 DPR 的大页面上把内存打爆。

3.1 为什么位图必须走字节预算

先算一笔账。一张 A4 页面按 scale 渲染成 PNG：

场景渲染倍率单页位图量级10 页合计
普通屏幕，适配宽度~1.0×约 0.3 – 0.8 MB约 3 – 8 MB
2× DPR 放大查看~2.0×约 1.5 – 4 MB约 15 – 40 MB
极限缩放（scale 上限 5.0）~10×可达 20 MB 以上理论 200 MB+

条数上限是 10，但那 10 条里装的可能是 8MB，也可能是 200MB。所以必须再加一个以字节为单位的预算。项目的实现是在 LruCache 构造时传入一个称重函数（src/shared/cache/LruCache.ts）：

const renderedPageCache = new LruCache<string, Uint8Array>(
  10,                              // maxEntries
  64 * 1024 * 1024,                // maxWeight = 64MB
  (value) => value.byteLength,     // 每一页的权重 = 它的真实字节数
);

淘汰条件是两个的或关系：entries.size > maxEntries || totalWeight > maxWeight。任一超标就从头淘汰最旧的，直到两个条件同时满足。这是一种很标准的"条数 + 容量"双限 LRU，浏览器自己的 HTTP 缓存、Redis 的 maxmemory 都是同一思路。

3.2 另外三个值得讲的细节

在途请求合并（in-flight dedup）

除了结果缓存，还有 structureRequests / renderRequests 两张 Map<key, Promise>。同一个键正在请求中时，第二次调用直接返回同一个 Promise，而不是再发一次 IPC。

为什么需要：虚拟滚动时同一页可能在几帧内被多次请求（组件重挂载、缩放连续变化）。没有合并就会出现"同一页渲染 3 次、后两次结果被丢进缓存"的纯浪费。finally 里删除条目，保证请求结束后不积压。

DPR 封顶在 2

PdfPage.tsx：Math.min(window.devicePixelRatio || 1, 2)。

在 3× 屏上按真实 DPR 渲染，像素量是 2× 时的 2.25 倍，而肉眼对文字锐度的感知提升已经很小。这是一个显式的"质量 vs 内存"折中，而且封顶值写死在唯一一处，容易调整也容易被 review。

关闭时按前缀清理

close(sessionId) 在 IPC 的 finally 里执行 deleteWhere(key => key.startsWith(sessionId + ":"))。

因为所有键都以 sessionId 开头，一次前缀匹配就能把该文档的所有缓存清干净——包括不同缩放倍率的多个位图条目。这就是"键的设计要支持生命周期管理"的一个实例。

二进制而不是 JSON 数组

render_pdf_page 返回 tauri::ipc::Response，直接送 Vec<u8>。

若返回 number[]：一个 1MB 的 PNG 会变成上百万元素、约 7MB 的 JSON 文本，再经历序列化 → 传输 → 解析 → Uint8Array.from。二进制通道省掉的不仅是带宽，更是整个 JSON 编解码过程。

「为什么两个缓存的淘汰策略不一样？」

"因为条目体积的方差不同。文字结构每页几 KB 到几十 KB，波动很小，所以条数就是体积的合理代理，24 条足够了。页面位图不一样——适配宽度时一页几百 KB，放大到 scale 5 可能二十几 MB，跨度两个数量级。只限条数的话，10 条里装的可能是 8MB，也可能是 200MB，内存就失控了。所以我给它加了一个 64MB 的字节预算，权重函数取 byteLength，淘汰时两个条件取或。另外同一个键的在途请求会复用同一个 Promise，避免虚拟滚动时同一页被重复渲染。"

4三套坐标系：同一个页面上有几种「坐标」

这一题最容易被答错，因为直觉上会觉得"应该统一成一种"。

结论：项目里同时存在两种坐标表示，按用途分配：只用于渲染的（文字结构）存绝对点；需要持久化或跨尺寸复现的（搜索命中、批注）存归一化 0..1 比值。README 说的"坐标同源"指的是同一次 MuPDF 计算，不是字面上同一个单位。

4.1 为什么"归一化"对批注是必需而不是优化

假设你改用绝对点存批注（比如 left: 412.7，单位是 PDF 点）。用户在笔记本上标注了一个词，之后：

  • 在外接 4K 显示器上打开 → 渲染倍率变了，但坐标是"点"所以还好（因为点与屏幕无关）；
  • 但只要渲染路径中任何一步引入了 DPR 或 CSS 像素的换算，绝对点就必须知道当时的倍率才能还原——而倍率没被存下来；
  • 更实际的问题是：批注数据的消费者很多（缩略图、侧栏列表的预览、导出、打印），每个消费者用的尺寸都不同。存比值意味着每个消费者都只需要乘自己的容器尺寸，不需要回溯"当时是什么环境"。

所以归一化在这类"标注型数据"上是标准做法，它把"环境依赖"从数据里彻底剥离了。

反例：如果强行统一成一种坐标

统一成绝对点 → 批注在缩放/换屏后会漂移，需要靠"记住当时的 scale"来补救，数据模型立刻变复杂。
统一成归一化 → 文字层每渲染一次都要做乘法，且选区几何需要反向换算；更麻烦的是，文字 span 的 fontSize 等属性本身就必须是点单位（fontSize * displayScale 才是 CSS 字号），强行归一化会让文字层逻辑割裂。按用途分两种，比强行统一更简单。

「批注坐标为什么用归一化？」

"因为批注是要存盘、而且要在不同尺寸的容器里被复现的数据。归一化成 0..1 的比值之后，任何消费者只需要乘自己的容器尺寸——缩略图、侧栏预览、打印、导出都各自乘各自的，不需要知道标注发生时是什么环境。如果存绝对点，就必须额外记录'当时的渲染倍率'才能还原，数据模型一下就复杂了。同一份数据里，页面文字结构仍然是绝对点，因为它只在一次渲染里用一次，乘个 displayScale 就够了，没必要多绕一层。所以项目里是两种单位，判断依据就是'要不要落盘'。"

5搜索与文本归一化：为什么不能直接 find

这一节涉及 Unicode，是很多人完全没想过的问题。

结论：PDF 里的文字和用户输入的查询词，在 Unicode 层面经常"看起来一样但字节不同"。所以搜索前必须把两边都做 NFKC 归一化 + 小写 + 空白折叠；而归一化会改变长度，因此必须同时维护一张「归一化位置 → 原始位置」的映射表，否则搜到了也定位不到。

5.1 具体是哪些字符会对不上

PDF 是从排版文件生成的，里面存的往往不是"正常人会输入的字符"：

情况PDF 里可能是用户会输入直接比较的结果
连字（ligature）ﬁ（U+FB01，一个字）fi（两个字）搜不到
全角字母Ａ（U+FF21）A（U+0041）搜不到
带圈数字①（U+2460）1（U+0031）搜不到
不同的空格不换行空格 U+00A0 / 制表符普通空格 U+0020搜不到
软连字符U+00AD（不可见）（无）中间多一个字符

NFKC 归一化（Compatibility Decomposition + Canonical Composition）正好处理前四类：ﬁ → fi、Ａ → A、① → 1、各种 Unicode 空白 → 普通空格。项目在 infrastructure/search/normalizer.rs 里逐字符做这件事。

5.2 关键难点：归一化会改变长度

这是整件事的核心。ﬁ 是 1 个字符，归一化后变成 fi 是 2 个字符；① 是 1 个，变成 1 还是 1 个但你不知道下一个会不会膨胀。所以归一化后的下标和原始字符串的下标不再一一对应——在归一化串里找到"位置 37"，无法直接知道它在原文里的位置。

项目的解法是：归一化时不为"字符"建索引，而是为归一化产生的每一个字符都记一条回指到源符号的记录。

5.3 还有两个"扫掉真实痛点"的细节

跨行连字符还原

PDF 排版会把长单词按拼音/音节断行，写成 inter-\nnational。用户搜 international 应该命中。

代码里的判断很谨慎：只有当 - 的前一个非空白字符和后一个非空白字符都是字母数字时才折叠。这样 well-\nknown 会还原，但列表里的 - 项目一 不会被误折叠。

软连字符直接丢弃

U+00AD（soft hyphen）是一个"只在换行处才显示"的隐形字符，PDF 里常出现但用户永远不会输入它。

代码在归一化第一步就 if symbol.text == "\u{00ad}" { continue; } 整条跳过——它连一个 NormalizedUnit 都不产生，所以也不会污染位置映射。这类字符如果留着，会让"整词匹配"永远失败。

空白折叠避免误合并

归一化时如果当前字符是空格、而结果串结尾已经是空格，就跳过。否则 PDF 里连续多个定位空格会让"搜两个词"变成"搜一个含多空格的串"，归一化查询词之后长度对不上。

上下文按「字符」而非「字节」截取

context(source, start, end, 32) 用 char_indices().rev().nth(radius) 往前走，而不是简单 start - 32。

因为 source[..start] 在 UTF-8 里按字节切片，切在汉字或 emoji 中间会直接 panic。测试 context_does_not_split_unicode_characters 就是守这一条的。

「搜索为什么要先做 NFKC 归一化？」

"因为 PDF 里的文字经常和用户输入的不是同一批码点。比如连字 ﬁ 是一个字符，用户输的是 fi 两个；全角 Ａ 和半角 A 码点不同；还有各种不换行空格和不可见的软连字符。直接比较就是搜不到。难点不在于归一化本身，而在于归一化会改变长度——一个 ﬁ 变成两个字符之后，归一化串的下标和原文下标就错位了。所以我在归一化的同时为每一个归一化出来的字符都记一条回指记录，保存它对应的原始 source 区间和字符矩形。命中后取这些区间的最小起点和最大终点，就能回到原串取上下文、同时拿到 rects 做高亮。另外跨行断词的连字符也会还原，但只在前后的非空白字符都是字母数字时才折叠，避免把列表项前面的短横线也吃掉。"

6原子写文件：为什么需要三行"多余"的代码

这是"用户数据不能丢"这条约束最直接的体现。

结论：直接 fs::write(path, data) 的问题是——如果写到一半进程崩溃，你既丢失了新数据，也丢失了旧数据。正确做法是"写临时文件 → fsync → 原子替换"，让目标文件永远处于"完整的旧版"或"完整的新版"两种状态之一，不存在中间态。

6.1 为什么 sync_all 必须在替换之前

这是最容易漏掉、也最能显示功底的一点。文件系统有自己的页缓存。如果不 fsync 就直接替换：

写入临时文件 → 数据还在页缓存 → 原子替换（此时"文件名"指向了内容尚未落盘的 inode） → 断电

结果是文件名换了，但新内容还没写进磁盘——目标文件变成空或半截。所以 fsync 的目的不只是"保证数据安全"，更是保证替换这个动作指向的内容是真实存在的。顺序不能颠倒。

6.2 TemporaryFileGuard 与那些"多余"的健壮性

整个流程里有两处看起来过度设计的细节，其实都是在处理真实边界：

代码如果去掉会怎样
TemporaryFileGuard + Drop 删临时文件任何一步 ? 提前返回，都会在目标文件旁边留下垃圾。用户会在文档目录里看到一堆 .xxx.tmp。测试 failed_generation_keeps_the_existing_destination 正是验证"生成失败后目标内容不变、且目录里只剩 1 个文件"。
guard.disarm()如果替换成功后 guard 仍然 armed，它会立刻把刚写好的文件删掉——一个极其隐蔽的自毁 bug。
导出后重新读回验证（HTML 检查 <!doctype html> 头尾；PDF 重新 open 并检查 page_count > 0）生成的 HTML/PDF 可能因为编码、样式或引擎问题而"写成功但内容是空的"。验证失败会返回 InvalidExportOutput，让整个写入流程回滚到旧文件——宁可报错，也不交付坏文件。
这体现了什么工程判断

写文件这类"看起来不会失败"的操作，真正的风险不是"写不进去"，而是"写进去了但内容不对"。所以项目在原子替换之前加了内容校验，把"坏文件"转化成了一次可回滚的失败。

「原子写为什么要这么多步？」

"直接 fs::write 到目标文件的风险是——写到一半崩溃，新数据没了，旧数据也被截断了，用户双份损失。所以做法是写同目录的临时文件、sync_all 落盘、再用 MoveFileExW 带 REPLACE_EXISTING 原子替换。sync_all 必须在替换之前，因为它在页缓存里待着的时候替换，会出现'文件名换了但内容还没落盘'的状态。临时文件必须在同目录，因为跨卷 rename 不保证原子，会退化成复制加删除。另外我用一个 Drop guard 保证任何一步出错都清掉临时文件，替换成功后 disarm 掉它。最后，写完之后会重新读回来验证一遍内容——HTML 检查头尾标签，PDF 重新打开检查页数，不合格就把整个写入回滚掉，宁愿报错也不交付一个坏文件。"

7关闭事务与乐观并发

两件都是"并发下如何不丢用户数据"的问题。

结论：关闭文档被拆成询问 → 提交 → 释放三个阶段，破坏性操作全部集中在最后一个阶段。这样"用户在第三个文档上按了取消"时，前两个文档的状态一点都没被改过。

7.1 为什么"边问边关"是错的

直觉写法是遍历标签页，逐个问"要保存吗"，答完就立刻关掉。问题是：

  • 用户在第 1 个文档选了保存 → 文档被关掉、session 释放；
  • 走到第 3 个文档，用户改主意按了取消；
  • 此时第 1、2 个已经关了，无法回退。用户看到的是一个"取消了但结果已发生"的界面——这是最伤信任的一类交互 bug。

7.2 实现上的一个细节

runCloseTransaction 里，阶段 A 的结果被收集到 prepared 数组里带着走：

const prepared: Array<{ candidate; preparation }> = [];
for (const candidate of candidates) {
    const preparation = await context.prepare(candidate);
    if (preparation.status === "cancelled") return { completed: false, cancelledAtId: candidate.id };
    prepared.push({ candidate, preparation });
}
// 阶段 A 全部通过后，才用 prepared 里的 commit 执行阶段 B

这解决了一个容易忽略的问题：用户在询问过程中可能切换了当前标签页。如果阶段 B 重新去 tabs.documents 里查，查到的是"现在"的状态，而不是"询问时"的那个文档。把 preparation 对象本身存下来，就保证了 commit 针对的一定是当初被询问的那一份。

7.3 Markdown 的乐观并发：revision

另一个"不丢用户数据"的机制。Markdown 会话里维护一个自增的 revision，每次编辑 +1。所有写操作都要求带上 base revision：

入口校验不校验会怎样
apply_edits(session, base_revision, …)不一致 → RevisionConflict两次编辑基于同一版本各自计算，后一次会静默覆盖前一次 —— 用户的输入凭空消失
save(session, revision)同上拿旧内容覆盖新内容
save_as(…, revision, …)同上另存为时写出一份过期快照
export_html / export_pdf(…, revision, …)同上导出的是用户以为早就改过的旧版本

特别注意最后一行：导出也校验 revision 是很多人不会想到的一点。它说明作者意识到"导出"同样是一个"基于某版本内容产生产物"的操作——如果版本错了，用户拿到的 PDF 和他屏幕上看到的不是同一份东西。

反例：为什么不能靠"禁用按钮"来防冲突

前端确实可以通过禁用输入框来降低冲突概率，但那只覆盖"单个窗口内、用户守规矩"的情况。revision 校验是后端的不变式——无论请求来自哪个窗口、顺序被怎样打乱、有没有并发，它都能兜住。把正确性放在服务端校验而不是 UI 状态上，是这个设计真正成熟的地方。

「关闭文档为什么要两阶段？」

"因为关闭是批量操作，而每个文档都可能需要用户决策。朴素写法是一边问一边关，但这会导致用户在第 3 个文档上按取消时，前两个已经关掉了、无法回退——这是个很伤信任的交互。所以我拆成三段：第一阶段全问完，只返回准备结果，不修改任何状态，任何一个取消就整体中止；第二阶段执行保存，保存是可重试的、非破坏性的；第三阶段才释放 session、关标签、写历史——所有不可逆的动作都集中在确定不会有取消分支之后。另外，第一阶段的结果会带着走而不是重新查，避免用户在询问过程中切换标签页导致提交对象错位。"

8错误契约与 IPC 边界（含一处要如实说的现状）

这一节包含一个「设计意图 ≠ 当前实现」的诚实说明。

结论：错误用枚举 AppError 建模（大约 25 个变体，每个都是一类明确的失败），这个设计是好的。但IPC 层面还没有把它序列化成结构化对象——当前是 serialize_str(&self.to_string())，前端只能拿到一个字符串。代码注释自己也承认"待专门的协议迁移"。

8.1 现状是什么样的

// error/app_error.rs —— 设计层面：强类型枚举
pub(crate) enum AppError {
    #[error("PDF password is required")]        PdfPasswordRequired,
    #[error("PDF password is invalid")]         PdfInvalidPassword,
    #[error("Markdown revision conflict: expected {expected}, received {actual}")]
    RevisionConflict { expected: u64, actual: u64 },
    ...
}

// 但序列化时，被"拍平"成了一个字符串
impl serde::Serialize for AppError {
    fn serialize<S>(&self, serializer: S) -> Result<S::Ok, S::Error> {
        serializer.serialize_str(&self.to_string())   // ← 类型信息在这里丢掉了
    }
}

代码注释写得很清楚："Keep the current IPC error contract compatible while the frontend still displays rejected command values as strings. A structured CommandError DTO can replace this in a dedicated protocol migration." —— 也就是说，这是一个有意推迟的迁移。

8.2 为什么这是问题

因为前端需要根据错误类型做控制流，而当错误只剩一个字符串时，判断逻辑就退化成了字符串匹配：

需求现在必须怎么做风险
PDF 需要密码 → 弹密码框匹配错误文案改一个字的文案就静默失效
保存冲突 → 提示"已在别处修改"匹配 RevisionConflict 的英文文案同上，且文案是英文、界面是中文
页面越界 → 直接忽略而不是报错匹配文案无法可靠区分

把"控制流"建立在"展示文案"上，是一个典型的接口设计缺陷——展示层的东西不应该被当成协议。

8.3 正确的做法（这也是一个很好的"下一步"回答）

#[derive(Serialize)]
#[serde(rename_all = "camelCase")]
struct CommandError {
    code: ErrorCode,          // 稳定枚举：PDF_PASSWORD_REQUIRED / REVISION_CONFLICT …
    message: String,          // 给人看的，可随意改、可本地化
    details: Option<serde_json::Value>,  // 结构化补充，如 {expected, actual}
}

然后前端只依赖 code，把 message 当纯展示。这个改动很小（一个 Serialize 实现 + 一个枚举 + 前端几处判断），但在面试里它有两个价值：证明你知道现状与理想的差距，并且能说出迁移路径。

面试时务必如实说

如果被问到"你的错误协议怎么设计的"，不要照着 README 的设计意图答。正确答法是："我设计的是枚举错误类型，每个变体对应一类明确的失败；但序列化这一层我暂时还是拍平成字符串的，因为前端当时只做展示，我在代码里留了注释标明这是一次待做的协议迁移。如果要修，就是加一个 CommandError DTO，把 code 和 message 拆开——前者稳定、后者可本地化。"
这个回答比"我做了结构化错误协议"强得多，因为它经得起你当场打开代码核对。

9Agent / RAG 落地：从现有架构长出来

这一节的重点不是"我要加 RAG"，而是"这个项目的地基比一般项目更适合做 RAG"。

结论：RAG 在这个项目里不是新玩具，而是被代码逼出来的需求——llm_service.rs 的请求校验里直接写着"请求文本过长，请先通过 RAG 缩小上下文"。而且因为项目已经有 block/line/span 三级文字结构和坐标，分块可以按版式边界切，引用能直接指到具体矩形并高亮——这是绝大多数 RAG 做不到的。

9.1 需求已经被写死在代码里了

// application/services/llm_service.rs
if total > 96_000 {
    return Err(AppError::Llm(
        "请求文本过长，请先通过 RAG 缩小上下文".into(),   // ← 需求被写在错误文案里
    ));
}

同时还有 MAX_OUTPUT_TOKENS = 8192、MAX_OUTPUT_BYTES = 2MB 之类的上限。这意味着：现在用户把一篇长文档贴进 AI 助手，会直接撞上这堵墙。这是一个"当前已存在的功能缺口"，而不是"我想加的新功能"——在面试里这种叙述方式的力量完全不同。

9.2 骨架已经预留，但确实是空的

文件状态说明
application/ports/agent_tool.rs空文件工具抽象端口的位置已经占好
domain/agent.rs空文件Agent 领域模型的位置
application/services/agent_service.rs空文件编排服务的位置

MCP 那一侧有一个非常好的注释，值得原封不动记住：

/// It only preserves the boundary.

这句话本身就是最好的回答模板：先说"我建好了边界、推迟了实现"，比说"我做了 Agent"可信得多，而且面试官一打开文件就能验证。

9.3 你的地基为什么特殊：分块能按版式，而不是滑窗

9.4 LangChain 那一题怎么答才安全

LangChain 没有 Rust 版本。所以无论你怎么想用，它在架构上不可能成为运行时（除非引入 Python sidecar，代价见上图）。安全的答法是主动把张力说清楚：

  1. 承认技术事实：LangChain 是 Python/JS 生态的编排框架，没有 Rust 实现。
  2. 列出三条代价：安装包体积、iOS 子进程限制、破坏现有的数据访问约束。
  3. 给出定位：把 LangChain 放在"离线实验与评测"位置——chunk 策略、嵌入模型选型、评测集，这些是一次性产出结论的工作，不需要进产品。
  4. 说清什么情况下会改主意：如果产品方向变成"必须以 Python 生态为核心"、或者移动端目标被放弃，那么 sidecar 方案的代价就值得付。

第 4 点很关键。它表明你的选型是有前置条件的，而不是"因为我不熟所以不用"。

守住「已设计 / 已实现」的边界

面试里最减分的不是"没做完"，是"说了但代码里没有"。关于 Agent 和 RAG，安全的表述边界是：

  • 可以说"已设计"：工具抽象端口、MCP 工具注册表 trait、权限边界、noop 实现。
  • 可以说"已实现"：LLM 客户端与流式输出、请求校验与上限、翻译服务、搜索与定位链路。
  • 不能说"已实现"：Agent 循环、工具调用、向量索引、检索、嵌入——那五个文件是空的，面试官一分钟就能打开看。

推荐句式："我把工具边界和权限模型设计好了，端口和 noop 实现都落地了，运行时还没做——那是我下一步要做的。"这句话完全经得起当场核对，而且证明了你知道该在哪里停。

「你要给这个阅读器加 RAG？为什么？」

"因为这是现在一个已存在的缺口，不是新功能。我的 LlmService 里有个校验，请求文本超过 96K 就直接报错，错误文案写的是'请先通过 RAG 缩小上下文'——也就是说用户现在把长文档贴进 AI 助手是直接撞墙的。

而这个项目做 RAG 的地基比大多数项目好，因为它已经有 block/line/span 三级结构和坐标。一般的 RAG 只能按固定长度滑窗切，会把表格切两半，也说不清一段话在第几页；我可以按版式边界切，每个 chunk 都带页面和矩形。所以引用能指到具体那一行字并高亮——搜索功能已经把这条路铺好了，SearchLocator 里就有 {page, page_y, rects}，覆盖层直接用百分比定位。

至于 LangChain，它没有 Rust 版本，不可能当运行时；我把它定位在离线实验和评测——用它做 chunk 策略实验和评测集，结论落成代码而不是落成依赖。"

10速查表：每节压成一行

面试前一晚只看这一页。

主题一句话结论反例（如果换个做法会怎样）
分层 依赖箭头始终由外向内；application 从不 import infrastructure，所以换引擎/换 IPC 都不穿透业务层。 不分层 → 任何单元测试都退化成集成测试，必须启动真实 DLL 和真实文件系统。
MuPDF 异常 setjmp/longjmp 全过程闭合在 C wrapper 的同一帧内；错误经 out-param 转为 Rust 的 Result。 直接调 → longjmp 越过 Rust 帧，跳过 Drop：句柄泄漏、锁死锁、UB。
每会话线程 fz_context 在线程本地存储，文档只能在其创建线程上使用，所以用 mpsc 序列化到专属线程。 用 Mutex<Document> → mutex 只保证互斥，不保证同线程；换线程用会拿到不同的 context，偶发内存损坏。
两层缓存 文字结构只限条数（24）；页面位图条数（10）+ 64MB 字节预算双限，权重取 byteLength。 位图只限条数 → 10 条里可能是 8MB 也可能是 200MB，高 DPR 大页面下内存失控。
二进制 IPC render_pdf_page 返回 ipc::Response 直接送 Vec<u8>。 返回 JSON number[] → 1MB 的 PNG 变成约 7MB 文本，还要经历完整编解码。
坐标系 文字结构存绝对点（只渲染一次）；搜索命中与批注存归一化 0..1（要落盘、要跨尺寸复现）。 批注存绝对点 → 缩放/换屏后漂移，必须额外记录"当时的倍率"才能还原。
NFKC 搜索 两边都做 NFKC + 小写 + 空白折叠；同时为每个归一化字符记录回指的 source 区间与 rect。 不归一化 → ﬁ/Ａ/①/软连字符全都搜不到；只归一化不建映射 → 搜到了也定位不到。
原子写 同目录临时文件 → sync_all → MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)；Drop guard 兜底清理。 直接 fs::write → 写一半崩溃，新数据没了，旧数据也被截断。跨卷 rename 不保证原子。
导出校验 写完后重新读回：HTML 查头尾标签，PDF 重开查 page_count > 0，不合格则整体回滚。 只判断"写成功" → 交付一个空的或损坏的导出文件，而旧文件已被覆盖。
关闭事务 询问 → 提交 → 释放三段；不可逆操作（释放 session／关标签）只在第三段。 边问边关 → 用户在第 3 个文档按取消时，前两个已经关了，无法回退。
乐观并发 Markdown 自增 revision，apply_edits / save / save_as / export_html / export_pdf 五个入口全部校验。 不校验 → 两次编辑基于同一版本各自计算，后一次静默覆盖前一次，用户输入凭空消失。导出不校验 → 交付的 PDF 和屏幕上看到的不是同一份。
错误契约 现状：枚举错误被 serialize_str 拍平成字符串，前端只能靠文案匹配。
目标：拆出 CommandError{ code, message, details }，控制流只依赖 code。		 把控制流建在展示文案上 → 改一个字的文案就让"弹密码框"这类逻辑静默失效。
RAG 分块 以 block 为最小单元按版式边界切，chunk 带 {page, rects}，引用可回跳并高亮到具体矩形。 固定滑窗 → 表格被切两半，出处只能说到"第 3 段"，做不到指到具体位置。
LangChain 没有 Rust 版本 → 不能当运行时；定位为离线实验与评测工具（chunk 实验、嵌入选型、评测集）。 硬上 Python sidecar → 安装包带 Python、iOS 禁止 fork/exec、打破"数据访问全由 Rust 负责"的约束。
最后三条通用提醒

1. 代码是现状，README 是意图。被问到任何"你的设计是什么"时，先在心里确认一句"代码里真的是这样吗"。这份文档里第 8 节就是一个现成的例子——设计是枚举、实现是字符串。

2. 讲不出"为什么"的设计，等于没设计。每一节的反例栏就是"为什么"的来源：先讲朴素做法会出什么问题，再说这个设计的约束条件，最后说结论。

3. 主动说出代价。Tauri 的 WKWebView 差异、前端 0 个测试、分层目前只靠约定没有 ESLint 强制——这些都是加分项，因为面试官真正想确认的是"你知不知道自己项目的边界在哪"。
